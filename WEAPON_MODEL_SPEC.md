# Weapon Model Handoff Spec

**Purpose.** This document is the complete contract for replacing OPERATOR's
procedural weapon models with better-looking ones. Hand this file (and nothing
else) to whoever is authoring the new models. If a returned model satisfies
everything here, it drops into the game with no code changes and every existing
animation, IK solve and ADS alignment keeps working.

Validate any returned model with:

```
node tools/validateWeaponModel.js <path-to.glb> <weaponId>
```

That script mechanically checks every rule below and prints exactly what is
wrong. A model that passes it is guaranteed to fit.

---

## 1. Which files currently make the guns

Every weapon is generated by a small script under `tools/builders/`, assembled
from boxes and cylinders. These are the files being replaced:

| Weapon id | Builder file | Output |
|---|---|---|
| `rifle` | `tools/builders/RifleBuilder.js` | `assets/models/weapons/rifle.glb` |
| `pistol` | `tools/builders/PistolBuilder.js` | `assets/models/weapons/pistol.glb` |
| `shotgun` | `tools/builders/ShotgunBuilder.js` | `assets/models/weapons/shotgun.glb` |
| `smg` | `tools/builders/SMGBuilder.js` | `assets/models/weapons/smg.glb` |
| `sniper` | `tools/builders/SniperBuilder.js` | `assets/models/weapons/sniper.glb` |
| `rocket_launcher` | `tools/builders/RocketLauncherBuilder.js` | `assets/models/weapons/rocket_launcher.glb` |
| *(projectile)* | `RocketLauncherBuilder.js` → `buildRocketProjectilePattern()` | `assets/models/weapons/rocket_projectile.glb` |

Shared helpers live in `tools/builders/WeaponBuilderKit.js` (`box`, `cyl`,
`socket`, `validateSockets`). All are run by `node tools/generateWeaponModels.js`.

**Two ways to deliver a replacement — either is fine:**

- **(A) A rewritten builder script.** Same filename, same exported function
  name, still emitting a `THREE.Group`. Keeps the project fully procedural and
  regenerable. Preferred.
- **(B) A finished `.glb`.** Dropped straight into `assets/models/weapons/`.
  In this case the matching builder becomes unused; say so and it gets deleted.

## 2. Axis convention (non-negotiable)

Right-handed, Y-up, and **−Z is forward**. This is Three.js's default and is
enforced project-wide (`COORDINATE_CONVENTIONS.md`).

- The weapon's root node **must** be named `Root_Weapon`.
- `Root_Weapon`'s local **−Z points down the barrel, out of the muzzle**.
- `+Y` is the top of the weapon (where sights sit). `+X` is the shooter's right.
- The weapon must be modelled at **identity rotation** — no corrective
  rotation baked into the root. A weapon held facing world-forward with zero
  rotation must already point the right way.

Getting this backwards is the single most common failure. If the gun renders
pointing at the player, the root is rotated 180°.

**Scale is metres, 1:1 real world.** A rifle is ~0.9 m long, not 90.

## 3. Required sockets

Sockets are empty `Object3D` nodes (no geometry) parented under `Root_Weapon`.
All six are **mandatory on every weapon**; the launcher adds a seventh.

| Socket | Meaning | Consumed by |
|---|---|---|
| `Socket_Grip` | Trigger hand's palm position | Two-bone arm IK (both perspectives) |
| `Socket_GripSecondary` | Support hand's palm position | Two-bone arm IK |
| `Socket_Muzzle` | Muzzle tip — flash, tracers, projectile spawn | Ballistics, VFX |
| `Socket_Magazine` | Where the magazine seats | Reload animation, dropped-mag physics |
| `Socket_Ejection` | Case ejection port | Casing physics |
| `Socket_Optic` | **Rear of the sight**, where the eye lines up | ADS alignment |
| `Socket_ShoulderRest` | *(launcher only)* Where the tube meets the shoulder | `shoulderMounted` grip |

### Socket orientation matters for two of them

- **`Socket_Muzzle`** — local −Z down the barrel. Tracers and rockets launch
  along this axis.
- **`Socket_Optic`** — local −Z out through the lens toward the target, local
  +Y is the shooter's "up" through the sight.

Everything else only needs correct **position**.

### Socket_Optic is the one to get exactly right

ADS positions the camera `eyeRelief` metres **behind** `Socket_Optic` along its
−Z, then aligns the bore. Put it at the **rear aperture / eyepiece** — the
point your eye would actually sit behind — **not** the centre of the optic and
not the front lens. If this is wrong, aiming feels wrong on that weapon only.

## 4. Named moving parts

These nodes are animated procedurally at runtime by `WeaponPartAnimator.ts`.
The node must be a **real child group that can be translated independently**,
with its geometry underneath it.

| Node name | Motion | Required on |
|---|---|---|
| `Bone_Magazine` | Hidden on `magazine_detach`, shown + reseated on `magazine_attach` | rifle, pistol, shotgun, smg, sniper, rocket_launcher |
| `Bone_ChargingHandle` | Racks along local **±X**, ~0.03 m, springs back | rifle, shotgun, smg, sniper |
| `Bone_Pump` | Slides along local **+Z** (toward the shooter), ~0.08 m, returns | shotgun only |

Notes:
- `Bone_Pump` travelling **+Z** is correct — the barrel is −Z, so racking the
  pump *backwards* is positive Z. Easy sign to get wrong.
- The magazine gets hidden outright during a reload, so it must not be welded
  into the receiver mesh.
- Sniper and shotgun also cycle between shots (bolt / pump), driven by the
  same nodes.

## 5. Per-weapon targets

Current socket positions, in metres, relative to `Root_Weapon`. **Treat these
as the target envelope, not gospel** — a better-proportioned model should move
them to wherever is anatomically right on the new geometry. What matters is
that they stay *consistent with the mesh*: `Socket_Grip` on the actual grip,
`Socket_Muzzle` at the actual muzzle.

If the new model changes overall length significantly, say so — a couple of
hip-rest offsets in `WeaponProfile.ts` may want re-tuning, which is a
one-line-per-weapon change.

### rifle — AK-pattern, ~1.2 m overall
```
Socket_Grip           [ 0.000, -0.100,  0.110]
Socket_GripSecondary  [ 0.000, -0.030, -0.300]
Socket_Muzzle         [ 0.000,  0.010, -0.800]
Socket_Magazine       [ 0.000, -0.140, -0.020]
Socket_Ejection       [ 0.050,  0.040, -0.050]
Socket_Optic          [ 0.000,  0.060, -0.200]
Parts: Bone_Magazine, Bone_ChargingHandle
```

### pistol — compact sidearm, ~0.22 m
```
Socket_Grip           [ 0.000, -0.075,  0.060]
Socket_GripSecondary  [-0.050, -0.050,  0.040]   (support hand cups the frame)
Socket_Muzzle         [ 0.000,  0.045, -0.180]
Socket_Magazine       [ 0.000, -0.075,  0.052]
Socket_Ejection       [ 0.030,  0.060, -0.020]
Socket_Optic          [ 0.000,  0.085, -0.020]   (rear notch)
Parts: Bone_Magazine
```

### shotgun — pump action, ~0.95 m
```
Socket_Grip           [ 0.000, -0.090,  0.090]
Socket_GripSecondary  [ 0.000, -0.035, -0.360]   (ON the pump — see below)
Socket_Muzzle         [ 0.000,  0.020, -0.820]
Socket_Magazine       [ 0.000, -0.025, -0.420]   (tube / shell port)
Socket_Ejection       [ 0.045,  0.030, -0.040]
Socket_Optic          [ 0.000,  0.055, -0.140]   (bead)
Parts: Bone_Magazine, Bone_ChargingHandle, Bone_Pump
```
**`Socket_GripSecondary` should be parented under `Bone_Pump`** so the support
hand physically tracks the forend as it racks. The IK re-solves every frame and
handles a moving target natively.

### smg — compact, folding stock, red dot, ~0.5 m
```
Socket_Grip           [ 0.000, -0.082,  0.070]
Socket_GripSecondary  [ 0.000, -0.052, -0.100]
Socket_Muzzle         [ 0.000,  0.012, -0.325]
Socket_Magazine       [ 0.000, -0.115, -0.020]
Socket_Ejection       [ 0.038,  0.032, -0.010]
Socket_Optic          [ 0.000,  0.053, -0.033]   (rear of the red dot)
Parts: Bone_Magazine, Bone_ChargingHandle
```
Needs a visible **red-dot optic body with a glass plane** on the rail.

### sniper — bolt action, long scope, ~1.15 m
```
Socket_Grip           [ 0.000, -0.085,  0.100]
Socket_GripSecondary  [ 0.000, -0.035, -0.340]
Socket_Muzzle         [ 0.000,  0.010, -0.940]
Socket_Magazine       [ 0.000, -0.105, -0.080]
Socket_Ejection       [ 0.040,  0.028, -0.020]
Socket_Optic          [ 0.000,  0.078,  0.035]   (rear of the EYEPIECE, +Z!)
Parts: Bone_Magazine, Bone_ChargingHandle (the bolt handle)
```
Note `Socket_Optic` is at **positive Z** — behind the receiver, at the
eyepiece. Eye relief is 0.12 m, the longest in the roster. Needs a real scope
tube with objective and eyepiece bells.

### rocket_launcher — shoulder-fired tube, ~1.1 m
```
Socket_Grip           [ 0.000, -0.080,  0.130]
Socket_GripSecondary  [ 0.000, -0.078, -0.340]
Socket_Muzzle         [ 0.000,  0.000, -0.600]   (front launch end)
Socket_Magazine       [ 0.000,  0.000, -0.520]   (breach-loaded warhead)
Socket_Ejection       [ 0.000,  0.000,  0.460]   (REAR — back-blast VFX)
Socket_Optic          [ 0.000,  0.086, -0.190]
Socket_ShoulderRest   [ 0.060,  0.048,  0.330]
Parts: Bone_Magazine (the visible loaded warhead)
```
`Socket_Ejection` is deliberately at the **rear** (+Z) here — it is reused as
the back-blast spawn point, not a case ejection port.

### rocket_projectile — the in-flight rocket
A small separate model, ~0.2 m, root named `Root_Projectile`. Flies along its
own −Z. No sockets required.

## 6. Materials and skins

- Use **`MeshStandardMaterial`**. The renderer is PBR with a real environment
  map for reflections.
- `flatShading: true` currently matches the game's low-poly look. A smoother
  model can drop it — either reads fine.
- **Leave `map` empty (or white).** A runtime skin system (`SkinManager.ts`)
  assigns one of three base-colour textures (`standard` / `desert` / `urban`)
  to every `MeshStandardMaterial` on the weapon and forces `color` to white.
  Any baked-in base colour map will be **overwritten**.
- Per-part colour differences should come from **separate materials per mesh**,
  which skinning preserves structurally.
- Keep it reasonable: these are viewmodels rendered every frame, plus a
  duplicate third-person prop. A few thousand triangles each is plenty.

## 7. Hard rules (things that will break the game)

1. **No skinned meshes / no armatures.** The project uses a rigid box-segment
   hierarchy driven by procedural transforms. A weapon is static geometry plus
   named nodes; skinning is not supported by the animation path.
2. **No fingers.** Hands are never individually articulated anywhere in this
   project — grip realism comes from shoulder/elbow/wrist rotation only. Do not
   model hands or arms into the weapon at all; the game supplies those.
3. **No baked animation clips in the .glb.** All weapon motion is procedural
   (`WeaponPartAnimator`) or comes from the project's own JSON clip format.
   Animation tracks in the file are ignored.
4. **Do not rename `Root_Weapon`, any `Socket_*`, or any `Bone_*`** — these are
   looked up by string.
5. **No lights or cameras** in the file.
6. Keep the origin at the **grip/receiver area**, roughly where the current
   models have it, so hip-rest offsets stay in the right ballpark.

---

## 8. What happens when models come back

1. Run `node tools/validateWeaponModel.js <file> <weaponId>` on each. It checks
   the root name, every socket's presence and axis, the animated part nodes,
   scale sanity, material types, and skinning/animation violations.
2. Fix whatever it reports (usually a rotated root or a missing socket).
3. Re-run the acceptance suites — `acceptance-docc` covers ADS eye-relief
   alignment and the bore convergence, `acceptance-docd` covers per-weapon
   behaviour and socket orientation, `acceptance-tps` covers the third-person
   carry pose.
4. Re-tune `hipRestPosition` / `eyeRelief` in `src/weapons/WeaponProfile.ts`
   only if the new proportions need it.

The IK, ADS math, reload beats, cycling actions and both perspectives all read
from the sockets — so if the sockets are right, the animations fit themselves.
