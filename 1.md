## 2. Foundational Definitions

Because this document may be read/executed by an AI agent or developer with no assumed context, every core concept is defined here explicitly.

**First-Person Shooter (FPS):** A game genre in which the player's view represents the eyes of their in-game character, and gameplay centers on aiming and firing weapons. The player typically sees only their arms and held weapon rendered in the foreground, never their full body.

**3D FPS Game:** An FPS rendered with real-time three-dimensional graphics — objects exist in a coordinate space with X, Y, and Z axes, the camera can rotate freely (look up/down/left/right) and translate through the space, and collision/physics operate in three dimensions. This is distinct from 2D "boomer shooters" which fake 3D with flat sprites.

**Three.js:** An open-source JavaScript library that provides a scene graph, cameras, lights, materials, geometries, and asset loaders on top of the browser's raw WebGL API, making real-time 3D rendering in a web browser practical without writing raw shader/GPU code for every object.

**Node.js:** A JavaScript runtime that allows JavaScript to run outside a browser (e.g., to run build tools, dev servers, and one-time asset-generation scripts on your local machine).

**npm (Node Package Manager):** The dependency manager used to install and version-lock third-party libraries (like `three`) as declared entries in a `package.json` file, rather than pasting library code into the project by hand or pulling it from a CDN at runtime.

**ES Modules (ESM):** The standard JavaScript module system using `import`/`export` statements, allowing code to be split across many files that explicitly declare what they need from each other. This project uses ESM exclusively — no global `<script>` variables, no CommonJS `require()`.

**Vite:** A modern front-end build tool that (a) runs a fast local development server with instant hot-module-reloading while building the game, and (b) produces an optimized, bundled, minified static build for production deployment.

**Scene graph:** Three.js's hierarchical structure of objects (`THREE.Object3D` and its subclasses like meshes, lights, and cameras) where each object can have child objects whose transforms (position/rotation/scale) are relative to their parent.

**WebGLRenderer:** The Three.js object responsible for actually drawing (rendering) a `THREE.Scene` from the perspective of a `THREE.Camera` onto an HTML `<canvas>` element using WebGL.

**Render loop / game loop:** A function that runs continuously, once per display refresh (via `requestAnimationFrame`), each iteration updating game state and then rendering a new frame — the heartbeat of any real-time game.

**Delta time:** The amount of real-world time (in seconds or milliseconds) that has elapsed since the previous frame, used to make movement/animation/physics speed independent of the actual frame rate the user's machine happens to achieve.

**Pub/Sub (Publish/Subscribe) pattern:** A messaging pattern where code can "publish" (emit) named events without knowing who, if anyone, is listening, and other code can "subscribe" (listen) to those named events without knowing who emits them — used here to keep unrelated systems (e.g., weapons and UI) decoupled from each other.

**Pointer Lock API:** A browser API that lets a web page capture the mouse fully (hiding the OS cursor, providing raw unbounded movement deltas), which is required for proper FPS mouse-look; it can only be activated in response to a genuine user gesture like a click, for security/privacy reasons.

**PBR (Physically-Based Rendering):** A material/lighting model that simulates how light realistically interacts with surfaces using measurable properties (base color, roughness, metalness, normal detail, ambient occlusion) instead of hand-faked shading, producing more realistic results across varied lighting.

## 5. Exact File-Level Specifications

### 5.1 `package.json`

Must declare:
- `"type": "module"` (enables native ESM in Node-executed files like `vite.config.js` and future `/tools` scripts).
- Scripts: `"dev": "vite"`, `"build": "vite build"`, `"preview": "vite preview"`.
- Dependencies: `three` (latest stable at time of build, pinned exact version, e.g. `"three": "0.16x.x"` — no caret range for the core engine dependency, to avoid silent breaking changes).
- DevDependencies: `vite` (pinned).
- Project `"name": "operator-fps"`, `"version": "0.1.0"`, `"private": true`.

### 5.2 `vite.config.js`

A minimal Vite config: sets the project root, ensures `/assets` and `/public` are served/copied correctly, and (in anticipation of Document 4's larger `.glb`/audio files) raises Vite's default asset inline-size threshold or explicitly excludes `/assets` from inlining so large binary files are always emitted as separate files, not base64-embedded into JS bundles. No plugins required yet beyond Vite's defaults, but the file should be structured so plugins (e.g., a future `vite-plugin-glsl` for custom shaders in Document 6) can be added without restructuring.

### 5.3 `index.html`

The single HTML shell for the entire game. Exact required contents:

- `<!DOCTYPE html>`, a `<head>` with charset, viewport meta tag (`width=device-width, initial-scale=1`), and a `<title>OPERATOR</title>`.
- A `<style>` block (or a linked minimal `style.css`) that: removes default body margin, sets `html, body { width:100%; height:100%; overflow:hidden; background:#000; }`, makes `#game-canvas` fill the viewport (`position:fixed; inset:0; width:100%; height:100%; display:block;`), and makes `#ui-root` an empty, absolutely-positioned full-viewport overlay div sitting above the canvas (`position:fixed; inset:0; pointer-events:none;` — individual future UI components will opt back into `pointer-events:auto` on themselves).
- Body contains exactly: `<canvas id="game-canvas"></canvas>`, `<div id="ui-root"></div>`, and `<script type="module" src="/src/main.js"></script>`.
- **No inline third-party script tags of any kind.** No CDN links. No embedded game logic in this file — it is a pure shell.

### 5.4 `src/main.js` — Entry Point

Responsibilities, in exact order:
1. Import `Engine` from `core/Engine.js`.
2. Import `GameStateManager` from `state/GameStateManager.js`.
3. Instantiate a single `Engine` instance, passing it a reference to the `#game-canvas` element.
4. Call `engine.start()` which kicks off the render loop (see 5.5).
5. Set `GameStateManager`'s initial state (in this document, immediately `PLAYING`, since no menu system exists yet — Document 5 will change this initial state to `MAIN_MENU`).
6. Contain **no other logic**. This file must remain tiny and purely orchestrational — it is the wiring point, not a place for implementation.

### 5.5 `core/Engine.js`

The central orchestrator, instantiated exactly once.

**Constructor responsibilities:**
- Accepts the canvas element (or its selector string).
- Constructs one `Renderer` instance (5.6), one `SceneManager` instance (5.7), one `Clock` instance (5.8), one `InputManager` instance (5.9), one `AssetLoader` instance (5.10).
- Initializes an internal array/Set of "updatable" objects (see below).
- Binds the render loop function's `this` context appropriately (or uses an arrow function class field) so it can be safely passed to `requestAnimationFrame`.

**Public methods:**
- `start()`: begins the `requestAnimationFrame` loop.
- `stop()`: cancels the loop (useful for cleanup/testing).
- `registerUpdatable(obj)`: adds `obj` (which must expose an `update(dt)` method) to the internal update list. This is **the** extension seam — Document 2's `PlayerController`, Document 3's `WeaponManager`, and all future per-frame systems plug into the main loop exclusively through this method, so `Engine.js` never needs to import or know about those future classes directly.
- `unregisterUpdatable(obj)`: removes it.

**Loop behavior each frame:**
1. Request next frame via `requestAnimationFrame`.
2. Get `dt = clock.getDelta()`.
3. Call `update(dt)` on every registered updatable, in registration order.
4. Call `renderer.render(sceneManager.getScene(), sceneManager.getCamera())`.
5. (This document adds no pause/resume gating — Document 5 will later wrap step 3 so updates halt while a menu is open. Note this explicitly in a code comment as a forward-looking seam.)

### 5.6 `core/Renderer.js`

**Sole responsibility:** own and configure the one and only `THREE.WebGLRenderer` instance. No other file may call `new THREE.WebGLRenderer()`.

Exact configuration required:
- Constructed with `{ canvas: <the game canvas element>, antialias: true }` (note: true antialiasing here is a placeholder default; Document 6 may swap to composer-based AA and disable this flag — leave a comment noting that).
- `renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2))` (capped to protect performance on high-DPI screens).
- `renderer.setSize(window.innerWidth, window.innerHeight)`.
- `renderer.shadowMap.enabled = true`.
- `renderer.shadowMap.type = THREE.PCFSoftShadowMap`.
- `renderer.outputColorSpace = THREE.SRGBColorSpace`.
- `renderer.toneMapping = THREE.ACESFilmicToneMapping`.
- `renderer.toneMappingExposure` set from a constant in `Constants.js` (e.g. `1.0`), not hardcoded inline.
- A `window.addEventListener('resize', ...)` handler that calls `renderer.setSize(window.innerWidth, window.innerHeight)` and updates the active camera (obtained via `SceneManager`) — `camera.aspect = window.innerWidth/window.innerHeight; camera.updateProjectionMatrix();`.

**Public methods:** `getRenderer()` (returns the raw `THREE.WebGLRenderer` for `Engine.js` to call `.render()` on), and `dispose()` for cleanup.

### 5.7 `core/SceneManager.js`

**Sole responsibility:** own the currently active `THREE.Scene` and `THREE.PerspectiveCamera`, and support swapping scenes later (Document 4's level loading).

Requirements:
- Constructs one `THREE.PerspectiveCamera(fov, aspect, near, far)` — `fov` read from `Constants.js` (default should be a realistic FPS value like 90), `near`/`far` reasonable defaults (e.g. `0.1` / `1000`), aspect from current window size.
- Constructs a default `THREE.Scene` on initialization (see 6.2 for exact temporary contents required in this document).
- Public methods: `getScene()`, `getCamera()`, `setScene(newScene)` (replaces the active scene reference — used by future `LevelLoader` in Document 4; this document just needs the method to exist and work correctly, e.g., verified with a unit test or manual swap-and-render check), `setCameraAspect(aspect)` (called by `Renderer.js`'s resize handler).

### 5.8 `core/Clock.js`

Wraps `THREE.Clock` internally (do not expose `THREE.Clock` directly to consumers — wrap it so its interface can be changed later without ripple effects).

Requirements:
- `getDelta()`: returns seconds elapsed since last call, **clamped to a maximum value** (e.g. `0.1`) to prevent huge simulation jumps after the browser tab was backgrounded/throttled.
- `getElapsed()`: total seconds since the clock started.
- `stepFixed(fixedDt, callback)`: implements a standard fixed-timestep accumulator pattern — accumulates real delta time each call, and invokes `callback(fixedDt)` zero or more times as needed to "catch up" to real time in fixed-size chunks, leaving any remainder accumulated for next call. This is provided now specifically so Document 2's physics/movement can be deterministic and frame-rate-independent; this document itself does not need to call it for anything beyond a proof-of-concept (e.g., driving the temporary test cube's rotation via fixed step in a way that demonstrates it works consistently).

### 5.9 `core/InputManager.js`

**Sole responsibility:** raw input capture and translation into named, rebindable "actions" — no gameplay logic.

Internal state:
- A `Set<string>` of currently-held raw key codes, updated via `window.addEventListener('keydown'/'keyup', ...)` using `event.code` (physical key, layout-independent) not `event.key`.
- A mouse-delta accumulator `{x: 0, y: 0}` updated via a `mousemove` listener **only while pointer lock is active**, reset to `{0,0}` every time `getMouseDelta()` is read (so each frame only sees that frame's movement).
- A `Set<number>` of currently-held mouse buttons via `mousedown`/`mouseup`.
- A key-binding map object, e.g.:
  ```js
  { moveForward: 'KeyW', moveBackward: 'KeyS', moveLeft: 'KeyA', moveRight: 'KeyD',
    jump: 'Space', sprint: 'ShiftLeft', crouch: 'ControlLeft', reload: 'KeyR',
    fire: 'Mouse0', ads: 'Mouse2', debugToggle: 'F3', pause: 'Escape' }
  ```
  loaded on construction from `SettingsStore.get('keyBindings', <defaults from Constants.js>)`.

Public methods:
- `isActionDown(actionName)`: looks up the bound key/mouse-button for `actionName` and returns whether it's currently held. **All future gameplay code (Documents 2+) must query input exclusively by action name through this method — never by raw key code** — this is what makes rebinding (Document 5) work without touching gameplay files.
- `getMouseDelta()`: returns and resets the accumulated `{x, y}` mouse movement since last call.
- `rebind(actionName, newKeyOrButtonCode)`: updates the binding map in memory and persists it via `SettingsStore.set('keyBindings', ...)`.
- `requestPointerLock(element)`: calls `element.requestPointerLock()`.
- `exitPointerLock()`: calls `document.exitPointerLock()`.
- Internally listens for the browser's `pointerlockchange` event and emits `EventBus` events `input:pointerlock:acquired` and `input:pointerlock:lost` accordingly — so no other module needs to touch `document.pointerLockElement` directly.

### 5.10 `core/AssetLoader.js`

**Sole responsibility:** the only place in the entire codebase permitted to instantiate `THREE.GLTFLoader`, `THREE.TextureLoader`, `THREE.AudioLoader`, `DRACOLoader`, or `KTX2Loader`.

Requirements:
- Constructs one instance of each loader above, wiring `DRACOLoader`/`KTX2Loader` into the `GLTFLoader` (`gltfLoader.setDRACOLoader(...)`, `gltfLoader.setKTX2Loader(...).detectSupport(renderer)`) so future compressed assets (Document 6) work with zero changes to loading call sites.
- Internal `Map` caches keyed by file path for models, textures, and audio buffers, so repeated `loadX(path)` calls with the same path return the already-loaded/parsed result instead of re-fetching.
- `async loadModel(path)`: returns a `Promise` resolving to the loaded glTF result (or a clone of the cached scene graph — must decide and document whether callers get a shared reference or an independent clone; recommended: return a `.clone()` of the cached scene so multiple instances of the same weapon/prop don't share transforms, while the geometry/material/texture data itself remains shared/cached for memory efficiency).
- `async loadTexture(path)`, `async loadAudio(path)`: same caching pattern.
- `async preload(manifest)`: accepts `{ models: string[], textures: string[], audio: string[] }`, loads them all (in parallel via `Promise.all`, or with a small concurrency limiter if needed), and emits `EventBus` event `assets:progress` with `{ loaded, total }` after each individual asset completes — this is the exact mechanism Document 5's loading screen will bind to.
- Must gracefully handle and log a clear console error (with the failing path) if any asset fails to load, rather than silently swallowing errors.

### 5.11 `core/EventBus.js`

A minimal, dependency-free pub/sub implementation.

Requirements:
- Exported as a **singleton** — the module itself constructs one instance and exports it (e.g. `export default new EventBus()`), so every file that does `import eventBus from './core/EventBus.js'` shares the exact same instance.
- `on(eventName, handler)`: registers `handler`, returns an unsubscribe function for convenience.
- `off(eventName, handler)`: removes a specific handler.
- `emit(eventName, payload)`: synchronously calls all registered handlers for `eventName` with `payload`; must not throw if there are zero listeners; should catch and console-error (not crash the whole emit chain) if an individual handler throws, so one broken listener can't break unrelated systems.
- Include a code comment documenting the **reserved event name convention** established so far, to be appended to (never redefined) by future documents:
  - `assets:progress` — `{loaded, total}`
  - `input:pointerlock:acquired` — no payload
  - `input:pointerlock:lost` — no payload
  - `game:stateChanged` — `{previous, current}`

### 5.12 `core/SettingsStore.js`

Requirements:
- Persists a single JSON object to `localStorage` under a **versioned key**, e.g. `'operator-fps-settings-v1'` — the version suffix allows future documents to safely change the settings shape without crashing on old saved data (a version bump means old data is simply discarded/reset to defaults, documented behavior, not a silent crash).
- `get(key, fallback)`: returns the stored value for `key` if present, else `fallback` (and does not persist the fallback until `set` is explicitly called).
- `set(key, value)`: merges `{[key]: value}` into the stored object and writes back to `localStorage` immediately (synchronous, since settings changes are infrequent and small).
- `getAll()`: returns the full parsed object (or `{}` if nothing stored yet or JSON parsing fails — must not throw on corrupted localStorage data, must fall back to an empty object and log a warning).
- `resetToDefaults()`: clears the stored key entirely.
- In this document, exercised only for persisting the `keyBindings` map (5.9) — full settings (video/audio/etc.) arrive in Document 5.

## 6. Verifying the Pipeline Works (Required Temporary Content)

### 6.1 Why This Section Exists

An empty scene proves nothing — a completely broken renderer and a correctly-configured-but-empty renderer look identical (a black screen). This document must produce **visible proof** that lighting, shadows, materials, and the render loop all function correctly together, before Document 2 builds real gameplay on top.

### 6.2 Required Temporary Scene Contents (in `SceneManager.js`'s default scene construction)

All of the following must be clearly wrapped in a comment block: `// TEMPORARY — pipeline verification only. Remove/replace in Document 2 (movement testing arena) and Document 4 (real levels).`

- One `THREE.AmbientLight` (soft fill, low intensity, e.g. color `#404050`, intensity `0.4`).
- One `THREE.DirectionalLight` (the "sun"): reasonably bright (e.g. intensity `1.0–1.5`), positioned above and to the side (e.g. `(10, 20, 10)`), with `castShadow = true`, a properly configured shadow camera (`shadow.mapSize.set(2048, 2048)`, and `shadow.camera.left/right/top/bottom/near/far` tuned to tightly fit a small ~20×20 unit test area — not left at Three.js's oversized defaults, which produce blurry/low-res shadows).
- One large `THREE.PlaneGeometry` (e.g. 50×50 units) with a `THREE.MeshStandardMaterial` (a plain gray color is fine — no textures required yet), rotated flat (`rotation.x = -Math.PI/2`), with `receiveShadow = true`.
- One `THREE.BoxGeometry` mesh (e.g. 1×1×1 unit), positioned a few units above the plane, `castShadow = true`, given a continuous rotation each frame (via being registered as an updatable, or driven directly — implementer's choice, but must be driven through `dt`, not a hardcoded per-frame increment, to prove delta-time-correct animation).
- The camera should start positioned to clearly frame this scene (e.g. `(0, 3, 8)` looking toward the origin) — no player controller exists yet, so the camera can simply be statically placed for this document's purposes.

**Visual acceptance check:** on load, you should see a gray floor, a spinning cube casting a soft, correctly-shaped shadow onto that floor, under warm/neutral directional lighting plus ambient fill — clearly demonstrating shadow mapping, tone mapping, and material rendering are all correctly configured.

## 7. Asset Pipeline Policy (Applies to This and Every Future Document)

Write `/tools/README.md` now with the following policy stated plainly, since this governs all future documents' asset handling:

> **Asset Generation Policy:**
> All 3D models, textures, animations, and audio files used by this game are real, static files committed under `/assets`. They are produced **once**, ahead of time, by scripts in this `/tools` folder (run manually via `node tools/<script>.js`) or authored directly in external tools (Blender, image editors, DAWs, etc.) and placed into `/assets` by hand. Scripts in `/tools` are permitted to use procedural/algorithmic generation internally, but their output must always be a saved file on disk — never in-memory geometry constructed live inside the running game. **The one exception is Document 1's single temporary test cube**, used only to verify the rendering pipeline before real content exists, and it is deleted once real gameplay/environments are built. If you are an AI agent or developer working on any future document in this series and find yourself writing `new THREE.BoxGeometry(...)` (or similar) inside `/src` gameplay code, stop — that content belongs in a `/tools` script that exports a real asset file instead.

No actual generation scripts need to be written yet in this document — `/tools` only needs this README to exist. Documents 2–4 will add real scripts (`generateWeaponModels.js`, `generateLevelGeometry.js`, etc.).
