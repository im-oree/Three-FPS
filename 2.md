DOCUMENT 2 of 6: Player Movement, Camera & Control System
(This is a standalone specification, the second in a six-document series for the "OPERATOR" FPS project. It assumes Document 1 — Foundation, Tooling & Core Engine Architecture — has been fully implemented and is sitting on disk exactly as specified. Do not build weapons, animation, real levels, menus, or HUD from this document — those are Documents 3–5.)

1. Purpose & Scope of This Document
Document 1 produced an empty engine shell: a renderer, a scene manager, input capture, an event bus, and a spinning test cube viewed from a static camera. This document's job is to turn that into a living, controllable first-person player — smooth Call of Duty–style movement (walk, sprint, crouch, slide, jump) and mouse-look, governed by a clean, explicit state machine, tested inside a simple temporary test arena (a gray box room with a few obstacles).

By the end of this document, a person must be able to click into the game, look around fluidly with the mouse, and run, sprint, slide, crouch, and jump around a small test space, with movement that feels weighted and responsive rather than robotic or floaty — the tactile foundation that every later document (weapons, animation, levels) builds on top of.

Explicitly out of scope for this document: weapons of any kind, viewmodels, skeletal animation, real levels/environments, HUD, menus, audio playback, AI, multiplayer. Those arrive in Documents 3, 4, 5, and beyond. The player is, for now, an invisible capsule with a camera at its eyes — there is nothing to see of "yourself," which is correct and expected at this stage.

2. Foundational Definitions
First-person camera controller: A system that rotates a THREE.PerspectiveCamera in response to mouse movement — yaw (left/right turning) rotating around the world's vertical axis, and pitch (up/down looking) rotating the camera locally, clamped so the player cannot flip upside down or loop past straight up/down. Critically, the camera's rotation is driven by the mouse, but the camera's position is driven by an underlying physics/movement simulation, not the other way around.

Capsule collider: A simplified 3D collision shape — a cylinder with hemispherical caps on top and bottom — commonly used to represent a humanoid character for movement collision, because it slides smoothly over uneven ground and around corners far more robustly and cheaply than using the character's actual detailed mesh for collision.

Simulation vs. render separation: A design principle where the "true" state of the game world (player position, velocity, current movement mode) is tracked in plain data structures updated on a fixed, predictable time step, while the visual representation (where the Three.js camera/objects actually appear on screen each frame) is a read-only reflection of that simulation state, optionally smoothed/interpolated for visual fluidity. This prevents physics behavior from varying based on the user's frame rate.

Fixed timestep: Updating physics/movement logic in constant-size time increments (e.g., always exactly 1/60th of a second per step), regardless of how often the browser actually renders a frame, by accumulating real elapsed time and "spending" it in fixed chunks. This produces deterministic, consistent physics behavior across different hardware.

State machine: A formal pattern where an entity (here, the player's movement) can only be in exactly one of a fixed set of named states at any given time (e.g., IDLE, SPRINT, SLIDE), with explicit rules about which states can transition to which other states, preventing invalid or nonsensical combinations (e.g., sliding directly out of a standing idle with no run-up).

Slide (COD-style mechanic): A short, high-speed crouch-slide move, triggered by crouching while sprinting, that converts forward running speed into a fast, low-profile slide that decays back down to a stop (or into a crouch) over a brief duration — a signature movement-shooter mechanic used for repositioning, dodging, and sliding into cover.

Coyote time: A deliberate, small forgiveness window (named after cartoon physics) that allows a jump input to still succeed for a brief moment (e.g., 100ms) after the player has walked off a ledge and is technically already airborne, because strict "must be grounded this exact frame" jump logic feels unfair and unresponsive to players.

Head bob: A small, rhythmic, procedural up-down (and sometimes side-to-side) offset applied to the camera to simulate the natural bobbing motion of a walking/running human body, purely a visual/feel effect layered on top of the true camera position — it must never affect actual hit-detection or movement physics.

Stamina system: A resource (often visualized as a meter) that depletes while performing costly actions (sprinting, sliding) and regenerates during rest (walking/standing), used to prevent infinite sprinting and add a light resource-management layer to movement.

6. Movement Simulation — Detailed Behavior Specification
6.1 Simulation/Render Separation (Architectural Requirement)
PlayerMovement.js must maintain the player's authoritative state as a plain data object, independent of any Three.js object:

JavaScript

{
  position: THREE.Vector3,      // capsule base position (feet) or center — pick one convention and use consistently
  velocity: THREE.Vector3,
  yaw: number,                  // radians, horizontal facing
  pitch: number,                // radians, vertical look, clamped
  capsuleHeight: number,        // current height (changes on crouch/slide)
  isGrounded: boolean,
  groundNormal: THREE.Vector3,
  timeSinceLastGrounded: number // for coyote time
}
This object is updated inside Clock.stepFixed(FIXED_DT, (dt) => { ... }), called once per real frame from PlayerController.update(dt) (which is itself registered via engine.registerUpdatable(playerController)). PlayerCamera.js reads the resulting position/yaw/pitch after the fixed-step simulation has run each frame and applies them to the actual THREE.PerspectiveCamera, adding purely-visual, non-simulation offsets on top (head bob, landing dip, later documents' recoil/ADS) — the simulation itself never contains these cosmetic offsets.

6.2 Horizontal Movement Model
Read moveForward/Backward/Left/Right action states each fixed step, combine into a normalized 2D input vector in local (camera-yaw-relative) space, ignoring pitch entirely (looking up/down must never make the player move into the floor or fly upward — movement stays on the horizontal plane relative to facing direction).
Convert this local input vector into a world-space desired direction, then into a desired horizontal velocity by multiplying by the current max speed for the active movement state (walk/sprint/crouch — see 6.3/6.5 for exact values-as-constants).
Do not snap current velocity instantly to desired velocity. Instead, accelerate the current horizontal velocity toward the desired velocity using an acceleration constant (units/sec²) while grounded, and a separate, lower acceleration constant while airborne (limited "air control," a standard FPS feel convention — full control on the ground, sluggish redirection in the air).
When there is no movement input and the player is grounded, apply a friction/deceleration constant that brings horizontal velocity smoothly to zero rather than an instant stop.
All of the above (walkSpeed, groundAcceleration, airAcceleration, groundFriction) are named constants in Constants.js under a MOVEMENT group — no inline magic numbers.
6.3 Sprint
Active only while: sprint action is held, player is grounded, player has forward-ish movement input (within a configurable angle threshold of pure-forward — e.g., ±45°, defined as SPRINT_MAX_INPUT_ANGLE_DEG in Constants.js — so sprinting is disallowed while moving purely backward or fully sideways, matching COD convention), and StaminaSystem reports available stamina (see Section 9).
While active, target max horizontal speed uses sprintSpeedMultiplier × walkSpeed (constant-driven).
Sprint state also drives: a small FOV increase via PlayerCamera (Section 8), increased head-bob amplitude/frequency via HeadBob (Section 10), and faster footstep cadence via FootstepSystem (Section 11).
Releasing sprint, running out of stamina, initiating ADS (a flag reserved for Document 3 — this document must include a simple isADSActive boolean input to the sprint-eligibility check, defaulting to always false for now, so Document 3 can wire real ADS in later with zero changes to this file), or ceasing forward input all immediately end sprint (transitioning to WALK or IDLE).
6.4 Jump
Jump input triggers only if isGrounded === true OR timeSinceLastGrounded <= COYOTE_TIME_SECONDS (a constant, e.g. 0.1).
On trigger: set vertical velocity to a jump-impulse value computed from physics (v = Math.sqrt(2 * GRAVITY * DESIRED_JUMP_HEIGHT)), where GRAVITY and DESIRED_JUMP_HEIGHT are both named constants — the impulse itself must be derived, not itself a hardcoded magic velocity, so tuning jump height in Constants.js behaves predictably.
Immediately set isGrounded = false and transition PlayerState to JUMP/AIR (see Section 7).
No double-jump: while airborne, further jump presses are ignored until grounded again (or until the coyote-time window from a new ledge, which is correct/expected behavior, not a bug).
Gravity is applied continuously to vertical velocity every fixed step while airborne, clamped to a maximum fall speed (TERMINAL_VELOCITY constant) to prevent runaway acceleration through thin geometry at high fall speeds.
6.5 Crouch
While crouch action is active (per hold/toggle setting) and the player is grounded, capsuleHeight and the camera's eye-height offset both smoothly lerp (not snap) from standing values to crouch values over a short, constant-driven duration.
Move speed while crouched multiplies by crouchSpeedMultiplier (< 1.0).
Before allowing a transition back to standing height, an upward raycast/capsule check from the player's current head position must confirm sufficient headroom exists; if blocked, remain crouched (queue the stand-up to happen automatically the first fixed step headroom becomes available, e.g., after walking out from under a low obstacle) rather than clipping through geometry.
Crouching while airborne has no special effect in this document (no crouch-jump tech required at this stage) — simply disallowed/ignored while isGrounded === false, revisited only if a future document requires it.
6.6 Slide (Full Mechanic Specification)
Trigger condition: current PlayerState is SPRINT, player is grounded, and the crouch action transitions from not-pressed to pressed (edge-triggered, not level-triggered — holding crouch shouldn't repeatedly retrigger slides).

Sequence, once triggered:

Capture the current horizontal velocity's direction as the fixed slide direction for the duration of the slide (steering during the slide is limited, not eliminated — see step 4).
Immediately multiply current speed by a SLIDE_BOOST_MULTIPLIER constant (a burst of extra speed on initiation, capped at a defined maximum slide speed regardless of how fast the player was already sprinting).
Over the slide's duration (SLIDE_DURATION_SECONDS constant), decay speed along an ease-out curve (not linear) back toward zero (or toward normal crouch-walk speed if the player is still holding movement input at slide end) — implement via a normalized time-based easing function in MathUtils.js if not already present (add one, e.g. easeOutQuad(t)), not an ad hoc formula duplicated inline.
Simultaneously lerp capsuleHeight/camera eye-height down to slide height (can reuse or be slightly lower than crouch height — a distinct SLIDE_HEIGHT constant) and apply a small forward camera roll/tilt (a few degrees, SLIDE_CAMERA_TILT_DEG constant) via PlayerCamera's additive rotation offset system (Section 8), restoring both smoothly on slide end.
Player retains a reduced steering influence during the slide (a SLIDE_STEER_INFLUENCE constant between 0 and 1, applied to how much new WASD input can bend the fixed slide direction) but cannot re-accelerate to full sprint speed mid-slide.
Early exit conditions, all valid and expected:
Slide duration timer expires naturally → transition to CROUCH_IDLE/CROUCH_WALK if crouch is still held, else back to WALK/SPRINT based on current input.
Speed decays below a minimum threshold → same resolution as above.
Player releases crouch mid-slide → immediately end the slide and stand back up (subject to the same headroom check as 6.5) into WALK/SPRINT.
Player presses jump mid-slide → this is a valid "slide-hop"/jump-cancel technique; end the slide immediately and apply the normal jump impulse (6.4) using the slide's current momentum as the carried-over horizontal velocity — this must feel good and is a deliberate, expected COD-style movement tech, not an edge case to prevent.
A short cooldown (SLIDE_COOLDOWN_SECONDS constant) after any slide ends before another slide can be triggered, to prevent slide-spamming as a movement exploit.
All numeric parameters named above must exist as clearly-named entries in Constants.js under a SLIDE group.

6.7 Ground Detection
Each fixed step, cast a short ray (or small sphere-cast, whichever PlayerCollider.js implements — a simple downward THREE.Raycaster from the capsule's center toward its base, extended slightly past the capsule's bottom, is sufficient for this document's placeholder arena) against the registered collision geometry (in this document, TestArena's simple shapes — see Section 13) to determine isGrounded and groundNormal.
On a small step-up or gentle slope (within a configurable max slope angle constant), smoothly snap the player's vertical position to the ground surface rather than treating it as a launch/bounce.
On slopes steeper than the max walkable angle, treat the surface as effectively a wall for movement purposes (no snapping, normal gravity/collision applies) — full slope-sliding physics are not required in this document, just correct rejection of over-steep surfaces as walkable ground.
Track timeSinceLastGrounded, resetting to 0 every fixed step the player is grounded, incrementing otherwise — this directly feeds the coyote-time check in 6.4.
6.8 Landing
The fixed step where isGrounded transitions from false to true after having been airborne is the landing moment.
If the vertical velocity at the moment of landing exceeded a defined threshold (HARD_LANDING_VELOCITY_THRESHOLD constant), emit EventBus.emit('player:landed', { impactVelocity }).
PlayerCamera.js (or a small dedicated spring-offset helper it owns) listens for this and applies a brief additive downward camera dip that eases back to neutral over a short duration (a simple critically-damped spring or a hand-authored ease curve is acceptable) — purely cosmetic, layered on top of the true camera position, never affecting the simulation.
This event is also the intended hook for Document 3's temporary post-landing accuracy penalty and Document 5's landing sound — this document is only responsible for emitting it reliably and with a correct, physically-derived impact velocity, not for consuming it beyond the camera dip.
7. PlayerState.js — State Machine Specification
This file contains pure logic only — no Three.js objects, no rendering, easily testable in isolation.

States (exported as a frozen enum-like object):
IDLE, WALK, SPRINT, CROUCH_IDLE, CROUCH_WALK, SLIDE, JUMP, AIR, LANDING.

Core function: resolveNextState(currentState, inputSnapshot, physicsSnapshot) → nextState, where:

inputSnapshot contains booleans/values like { hasMoveInput, sprintHeld, crouchHeld, crouchPressedThisFrame, jumpPressedThisFrame }.
physicsSnapshot contains { isGrounded, horizontalSpeed, verticalVelocity }.
Legal transition rules that must be explicitly encoded (not left implicit/accidental):

SLIDE is reachable only from SPRINT (per 6.6's trigger condition) — attempting to trigger it from WALK, IDLE, or CROUCH must be a no-op.
JUMP/AIR is reachable from any grounded state given a valid jump trigger (6.4), including as a slide-cancel from SLIDE (6.6, step 6).
LANDING is a short-lived, auto-expiring state (a brief timer, constant-driven) entered automatically whenever AIR/JUMP transitions to grounded, which itself immediately resolves onward to IDLE/WALK/CROUCH_IDLE/CROUCH_WALK based on current input the moment its timer expires (or immediately, if no separate "landing pose" behavior is desired beyond the camera dip — the state exists primarily as a clean hook point for Document 3's animation system, not because it needs to block input).
CROUCH_WALK vs CROUCH_IDLE simply reflects whether there is current movement input while crouched.
Sprint cannot be entered while crouched; crouching while sprinting either ends sprint into CROUCH_WALK/CROUCH_IDLE directly, or triggers SLIDE per the edge-triggered rule in 6.6 — both must be explicitly handled, not ambiguous.
This module has zero dependencies on InputManager, Clock, or Three.js directly — PlayerController.js is responsible for gathering the raw snapshots each fixed step and calling resolveNextState, keeping this file pure and independently testable/reasoned-about. This is also exactly the module Document 3's AnimationStateMachine will read from to decide which animation clip to play.

8. PlayerCamera.js — Camera Ownership & Feel
Takes ownership of (but does not construct — receives via constructor injection from SceneManager.getCamera()) the single THREE.PerspectiveCamera established in Document 1.
Each frame, reads current yaw/pitch from the mouse-delta accumulator (InputManager.getMouseDelta()), scaled by SettingsStore-sourced sensitivity and optionally inverted for Y, and adds them into the simulation's yaw/pitch values (not directly onto the camera object — yaw/pitch are logically part of player facing/simulation state per Section 6.1's data shape, since e.g. movement-relative-to-facing depends on yaw).
Clamps pitch to a safe range (e.g. ±89°, MAX_PITCH_DEG constant) to prevent gimbal-flip.
Applies the simulation's resulting position/yaw/pitch to the actual THREE.PerspectiveCamera transform each render frame, then layers on top, in order: head bob offset (Section 10), landing dip offset (Section 6.8), and slide tilt (Section 6.6) — all additive, all cosmetic, all clearly separated so future documents (recoil kick, ADS zoom in Document 3) can add further additive layers without needing to touch or understand this document's internals.
Implements a generic FOV-modifier-stack API: applyFOVModifier(id, targetFOV, lerpSpeed) / clearFOVModifier(id), where multiple named modifiers (e.g., 'sprint', and later Document 3's 'ads') can be pushed/popped independently, and the camera's actual FOV each frame is resolved as a smooth blend toward whichever modifier(s) are currently active (simplest correct approach: track a target FOV that recalculates each frame based on active modifiers by priority/precedence rule you define — e.g., ADS always overrides sprint if both are somehow active — and lerp the actual FOV toward that target every frame, never snapping instantly). Sprint (6.3) uses this system now via a 'sprint' modifier id; this document must not hardcode a single-purpose "sprint FOV" field that would conflict with Document 3's future ADS FOV need.
Implements a generic camera shake/kick API: shake(intensity, duration) (a decaying random-offset shake, used now only for the landing dip if you choose to implement landing as a "shake" rather than a bespoke spring — either is acceptable as long as the API exists and is genuinely reusable) — this exact method is what Document 3's recoil and damage-feedback systems will call into later, so its signature must be finalized thoughtfully now, not revisited/broken later.
9. StaminaSystem.js
Tracks a normalized stamina value (0.0 to 1.0).
Depletes at a constant rate per second while sprinting or sliding is active; regenerates at a (likely different, slower) constant rate per second while neither is active, with a short regen-delay timer after depletion reaches zero before regeneration begins (prevents instantly re-sprinting the moment stamina hits zero).
Exposes hasStamina() (boolean, whether sprint/slide may currently be initiated — likely currentStamina > 0) and getCurrentValue().
Emits EventBus.emit('player:staminaChanged', normalizedValue) whenever the value changes meaningfully (e.g., on every fixed step it changes, or throttled slightly if needed for event-spam reasons — document whichever choice is made) — this is the exact data Document 5's stamina HUD element (if included) will bind to; this document must verify correctness via Debug.js's overlay (add a temporary debug line showing the live stamina value) since no real HUD exists yet.
10. HeadBob.js
A small, self-contained module computing a sinusoidal positional offset (primarily vertical bob, plus a subtler horizontal side-to-side sway forming a figure-eight motion, matching natural gait) as a function of elapsed "distance traveled while grounded" (not raw time — bob should tie to footfall rhythm relative to movement speed, not tick along even while standing still) or, more simply, elapsed time scaled by current speed — either approach is acceptable as long as bob frequency visibly scales with movement speed rather than being a fixed-rate wobble regardless of how fast the player is moving.
Distinct amplitude/frequency constant sets for WALK, SPRINT, and CROUCH_WALK states (near-zero/disabled for IDLE, AIR, and — noted for Document 3's future benefit — should be trivially disable-able via a flag for when ADS is added later, so include an enabled boolean input this document can just always pass as true for now).
Output is a plain {x, y, z} offset consumed additively by PlayerCamera.js — this module has no direct reference to the camera object itself, keeping it a pure, testable offset generator.
11. FootstepSystem.js
Watches current horizontal speed and isGrounded state each fixed step; maintains an internal distance/time accumulator that, once it crosses a speed-dependent threshold (faster movement → shorter interval between footsteps, i.e., a higher cadence), emits EventBus.emit('player:footstep', { surfaceType }) and resets the accumulator.
surfaceType is hardcoded to the literal string "concrete" in this document (there is only one surface in the placeholder Test Arena) — explicitly commented as a temporary stand-in, to be replaced in Document 4 with a real lookup against whatever surface the ground-detection raycast (6.7) actually hit.
This module must not play any audio. It only emits correctly-timed events. Verify correctness during development via a temporary EventBus.on('player:footstep', console.log) or a Debug.js overlay line — real audio playback is entirely Document 5's responsibility.
12. PlayerController.js — Top-Level Orchestrator
This is the file registered into Engine.registerUpdatable() and is the only /player file main.js needs to directly construct and wire up.

Responsibilities:

Owns instances of (or is constructed with references to) PlayerMovement, PlayerCollider, PlayerCamera, HeadBob, StaminaSystem, FootstepSystem, and holds the current PlayerState value.
Its update(dt) method: calls clock.stepFixed(FIXED_DT, (fixedDt) => { ...gather input snapshot, resolve next state via PlayerState.resolveNextState, run PlayerMovement's physics step for this fixedDt, run PlayerCollider's collision resolution, run StaminaSystem/FootstepSystem updates... }), then, once per real frame (outside the fixed-step callback), calls PlayerCamera's per-frame visual update (applying head bob, landing dip, etc., and reading fresh mouse-delta input for immediate, non-fixed-step-limited look responsiveness — look/camera rotation should feel instant and frame-rate-smooth even though movement physics is fixed-step, a deliberate and important distinction).
On construction, calls InputManager.requestPointerLock() bound to a user gesture (in this document, since no menu/click-to-play UI exists yet, a simple temporary one-time click listener on the canvas is sufficient to trigger the first pointer lock request — clearly commented as a placeholder that Document 5's "click to play" loading screen will formally own later).
Exposes read-only getters other future systems will need: getPosition(), getState(), isGrounded() — anticipating Document 3's weapon system needing to query player state (e.g., "is player moving/jumping" for spread calculations) without reaching into private internals.

14. Acceptance Criteria for Document 2
 Clicking into the game acquires pointer lock; mouse movement smoothly, correctly rotates the camera's yaw/pitch with no jitter, no drift, and correct clamping (cannot look past straight up/down, no flipping).
 Sensitivity and invert-Y are read from SettingsStore (even with no UI yet to change them, manually editing localStorage values must visibly change behavior on reload, proving the wiring is correct).
 WASD movement feels weighted — visible, smooth acceleration and deceleration, not instant velocity snapping.
 Sprint activates/deactivates correctly per all stated conditions (forward-ish input, grounded, stamina available) and produces a smooth FOV increase and increased head bob.
 Crouch smoothly lowers capsule/camera height, correctly reduces speed, and correctly refuses to stand back up under low obstacles until headroom is clear.
 Slide triggers only from sprint+crouch-press, produces the full speed-boost-then-decay curve, correct height/camera tilt transition, limited steering, and all three exit conditions (timeout, low-speed, crouch-release) work correctly.
 Slide-to-jump cancel works and correctly carries momentum into the jump.
 Slide cooldown correctly prevents immediate re-sliding.
 Jump has physically-derived height (verify by tuning DESIRED_JUMP_HEIGHT and confirming actual measured jump height matches), correct coyote-time forgiveness, and no double-jump exploit.
 Player correctly collides with all TestArena geometry: no falling through the floor, no clipping through walls/boxes, smooth step-up over the low platform, correct rejection of over-steep surfaces if any are included.
 Landing after a fall from height triggers a visible, smooth camera dip and a correctly-payloaded player:landed event (verify via console logging).
 Stamina depletes and regenerates correctly per the stated rules and correctly gates sprint/slide eligibility; live value is visible via a temporary Debug.js overlay line.
 Footstep events fire at a cadence that correctly scales with current movement speed, verified via console logging, with zero actual audio playback implemented.
 PlayerState.resolveNextState correctly enforces every stated legal-transition rule (spot-check by attempting to trigger a slide from IDLE, which must fail/no-op).
 All numeric tuning values introduced by this document live in Constants.js, none hardcoded inline anywhere in /src/player.
 PlayerCollider.js's constructor-injected collision data source is generic/documented clearly enough that a reviewer can confirm Document 4 could swap it without touching PlayerMovement.js or PlayerController.js.
 TestArena.js is fully isolated, clearly marked temporary, and could be deleted along with its single import line in main.js/PlayerController.js wiring with no other code changes required.
