## 2. Foundational Definitions

**Level:** A self-contained, pre-authored 3D environment (geometry, lighting, spawn points, collision data) that the player is placed into and plays within — as opposed to a randomly assembled or purely runtime-constructed space.

**Level metadata:** A separate, human-readable JSON file that accompanies a level's 3D scene file, describing everything about that level that isn't itself raw geometry: where the player should spawn, how the level should be lit, what fog settings apply, and — critically — which meshes within the scene file are meant to be used for **collision** rather than just visuals.

**Visual mesh vs. collision mesh:** In real game development, the mesh the player *sees* (detailed, high-poly, fully textured) is often a poor and expensive choice to run physics/raycasts against directly. A **separate, simplified proxy mesh** — invisible to the player, made of simple shapes roughly matching the visible geometry's silhouette — is used instead for movement collision and hit-detection raycasts, because it's cheaper to compute against and can be authored to avoid tiny geometric cracks/gaps that would otherwise snag a player capsule.

**Surface material tag:** A text label (e.g. `"concrete"`, `"metal"`, `"wood"`, `"gravel"`) attached to a piece of collision geometry, letting gameplay code (footsteps, bullet impacts) react appropriately to *what kind of surface* was involved in an interaction, rather than treating all surfaces identically.

**Skybox / environment map:** A large background image or cubemap surrounding the entire scene, used both to make outdoor areas look like they extend to a horizon/sky rather than ending abruptly in a void, and to provide realistic-looking reflections on shiny/metallic surfaces via image-based lighting.

**Fog:** A rendering effect that fades distant objects toward a chosen color, used both for atmospheric realism and as a practical performance/design tool to hide the level's far draw-distance boundary.

## 5. Level Metadata JSON — Required Schema

Every level ships a JSON file at `/assets/environment-meta/<levelId>.json` conforming exactly to this shape:

```json
{
  "id": "warehouse",
  "displayName": "Warehouse",
  "sceneFile": "/assets/models/environment/warehouse.glb",
  "collisionMeshNames": ["COL_Floor", "COL_Walls", "COL_Shelving", "COL_Catwalk"],
  "surfaceTags": {
    "COL_Floor": "concrete",
    "COL_Catwalk": "metal",
    "COL_Shelving": "wood"
  },
  "spawnPoints": [
    { "position": [0, 0, 0], "yaw": 0 },
    { "position": [15, 0, -10], "yaw": 180 }
  ],
  "lighting": {
    "ambient": { "color": "#40404f", "intensity": 0.5 },
    "directional": {
      "color": "#fff2df", "intensity": 1.2,
      "position": [40, 60, 20], "castShadow": true,
      "shadowFrustum": { "left": -30, "right": 30, "top": 30, "bottom": -30, "near": 1, "far": 150 }
    },
    "fog": { "color": "#1a1a1f", "near": 25, "far": 130 }
  },
  "ambientSoundKey": "ambient_warehouse_loop"
}
```

Field-by-field requirements:
- `collisionMeshNames`: exact object names (as authored in the `.glb`/DCC tool) of the meshes meant to serve as collision proxies — these are typically invisible in the final render (hidden via a material flag or simply excluded from the visual draw pass) and used only for physics/raycast queries.
- `surfaceTags`: a lookup from collision mesh name to surface material string, consumed by `SurfaceMaterialRegistry.js` (Section 9).
- `spawnPoints`: at least one, ideally multiple, world positions + facing yaw where the player capsule is placed at level start (multiple spawn points anticipate future multiplayer spawn rotation, but are used here simply by picking the first one, or one at random, for single-player).
- `lighting.directional.shadowFrustum`: **must be explicitly specified per level**, not left at a generic default — each level has a different physical size, and an oversized/undersized shadow camera frustum produces either blurry or clipped shadows. This is a deliberate correction of Document 1's temporary hardcoded test-scene values.
- `ambientSoundKey`: a string key (no actual audio file wiring happens in this document — that's Document 5 — but the field must exist now so Document 5 doesn't need to modify this schema later).

`LevelLoader.js` (Section 6) is the only module that reads and interprets this file.

## 6. `LevelLoader.js` — The Central Loading Pipeline

Responsibilities, in exact order, given a `levelId`:

1. Fetch and parse `/assets/environment-meta/<levelId>.json`.
2. Call `AssetLoader.loadModel(metadata.sceneFile)` to load the level's `.glb` scene graph.
3. Walk the loaded scene graph: for every object whose name matches an entry in `metadata.collisionMeshNames`, extract its geometry (or a bounding-volume representation of it — see `CollisionWorld.js`, Section 7, for exactly what form this takes) and register it into `CollisionWorld`, tagged with its corresponding `surfaceTags` entry (defaulting to a generic `"generic"` tag if a collision mesh has no explicit tag listed). These collision meshes should then be hidden from the visual render (set `visible = false`, or rely on them being modeled as extremely simple untextured proxies that are acceptable to leave invisible/culled) so players don't see crude collision geometry overlapping the detailed visual meshes.
4. Call `SceneManager.setScene(loadedScene)`, replacing whatever scene was previously active — and explicitly **dispose of the previous scene's resources** (geometries, materials, textures no longer in use) to avoid memory leaks when switching levels repeatedly (e.g., Training Range → Warehouse → Training Range during testing/play).
5. Instantiate `LightingRig` (Section 8) using `metadata.lighting`, attaching lights into the newly active scene.
6. Instantiate `SkyboxManager` (Section 9... see below, actually Section 10) if the level metadata calls for one (indoor-only levels like a fully enclosed Training Range may skip this; Facility, with its outdoor courtyard, requires it).
7. Select a spawn point (first in the list, or random — document the choice) and report it back to the caller (`main.js` or whatever orchestrates level start) so `PlayerController` can be positioned/reset there.
8. Emit `EventBus.emit('level:loaded', { levelId, spawnPoint })` once fully complete — this is a new reserved event name, to be appended to Document 1's documented `EventBus` convention list, and is what Document 5's loading screen will key its "loading complete" transition off of.

`LevelLoader` must also expose an `unloadCurrentLevel()` method performing the disposal half of step 4 in isolation, callable when returning to a main menu (Document 5) without immediately loading a new level.

## 7. `CollisionWorld.js` — The Generic Collision Registry

This is the most architecturally important file in this document, since it is the thing that proves Documents 2 and 3 were built correctly decoupled.

- Maintains an internal list of registered collision entries, each holding: a reference to the geometry/shape (a `THREE.Mesh` with real geometry is acceptable for this project's scale — full BVH-optimized collision is not required, though a comment should note that a bounding-volume-hierarchy acceleration structure would be the natural next optimization if level complexity grows significantly in the future, deferred to Document 6's performance pass if warranted), and its associated `surfaceTag`.
- Exposes exactly the same query interface Document 2's `PlayerCollider.js` was already written against (per Document 2's explicit forward-looking contract): `raycastDown(origin) → { point, normal, distance, surfaceTag } | null`, `raycastUp(origin, maxDistance) → hit | null`, `resolveHorizontalCollision(position, desiredDelta, capsuleRadius) → correctedDelta`.
- **Integration task (required, not optional):** open `PlayerCollider.js` from Document 2 and confirm/adjust its internals so these methods are now backed by querying `CollisionWorld`'s registered geometry instead of the old hardcoded `TestArena` box array — the *calling* code in `PlayerMovement.js`/`PlayerController.js` must require zero changes. If changes beyond `PlayerCollider.js`'s internals are needed, that indicates Document 2 was not built with sufficient separation, and this document must correct that coupling as part of delivering itself.
- Also exposes a `getAllCollisionMeshes()` accessor, used by `LevelLoader` step 3 and by `BallisticsSystem` (Document 3) — this document must register `CollisionWorld`'s full mesh list into `BallisticsSystem.registerHittable()` for every level load (each mesh tagged with its `surfaceTag` as hit metadata), so gunfire correctly produces surface-appropriate wall-impact effects in real levels, exactly through Document 3's existing, unmodified registration API.
- Must correctly **clear and re-populate** itself on every level load/unload (called from `LevelLoader`), so switching levels never leaves stale collision geometry from a previous level still active.

## 8. `LightingRig.js`

- Given a level metadata's `lighting` block, constructs: one `THREE.AmbientLight` (or `THREE.HemisphereLight`, if a more natural sky/ground light split is desired for outdoor-inclusive levels like Facility — implementer's choice, document which was used and why) from the `ambient` config, one `THREE.DirectionalLight` from the `directional` config with `castShadow` and the **explicitly per-level-specified** shadow camera frustum bounds (`shadow.camera.left/right/top/bottom/near/far` set directly from `metadata.lighting.directional.shadowFrustum`, not left at library defaults), and applies `scene.fog = new THREE.Fog(color, near, far)` from the `fog` config.
- Must also **detect and preserve any lights authored directly inside the level's `.glb` file itself** (Three.js's `GLTFLoader` will import `THREE.Light` nodes if the source file included them, e.g., localized point/spot lights for interior lamp fixtures) — these should be left active in the loaded scene graph as-is, in addition to the JSON-specified sun/ambient, giving level artists a way to add local lighting detail without needing new JSON schema fields for every fixture.
- Exposes a `dispose()` to cleanly remove its constructed lights when a level unloads (the glTF-embedded lights are disposed of naturally as part of the scene's own disposal in `LevelLoader`).

## 11. The Three Required Levels — Design Specification

### 11.1 Warehouse (`WarehouseLevel.js` + `warehouse.glb`/`warehouse.json`)

An indoor, industrial combat space: tall metal shelving units forming sightline-breaking corridors, stacked wooden crates/pallets as low cover, at least one forklift or similar industrial prop for visual interest, and a **mezzanine/catwalk level** reachable via a staircase, giving verticality (testing Document 2's jump/movement against real stairs and elevated collision geometry, not just the flat Test Arena). Requires: at least 2 spawn points, at least 3 distinct `surfaceTags` in actual use (e.g., `concrete` floor, `metal` catwalk, `wood` crates) so footstep/impact variety is genuinely exercised, and a mix of close-range (between shelving) and mid-range (across the main floor) sightlines.

### 11.2 Facility (`FacilityLevel.js` + `facility.glb`/`facility.json`)

A mixed indoor/outdoor space: a building interior (offices/hallways, tighter CQB angles, interior fill lighting) connected via a doorway or breezeway to an **outdoor courtyard or loading-dock area** under the directional sun light, providing at least one genuinely long sightline (50+ units) specifically to exercise the Sniper-class damage-falloff curves and general long-range hit registration from Document 3 in a way the Warehouse's tighter spaces cannot. Requires a working `SkyboxManager` application for the outdoor portion, and a visible, deliberate lighting contrast between the interior (artificial fill lights) and exterior (natural sun) zones.

### 11.3 Training Range (`TrainingRangeLevel.js` + `training_range.glb`/`training_range.json`)

A clean, well-lit, minimal shooting range: a firing line, open flat ground, and a set of **static target props** placed at clearly varied distances (e.g., near ~5m, mid ~25m, far ~50m) explicitly to validate Document 3's damage-falloff curve end-to-end in a real (not placeholder) environment. This level's purpose is **weapon-feel validation with zero AI dependency** — it must fully replace the role the Document 3 test dummies played, but with properly modeled, properly placed static props instead of throwaway boxes.

- Each target prop is registered into `BallisticsSystem.registerHittable()` (Document 3's unmodified API) with a `takeDamage(amount)` method, reacting visibly on hit (a knockback tilt, a color flash, or a simple "steel target clang and swing" animation — any clear, visible reaction is acceptable) via the same `combat:hit` event pipeline established in Document 3, with no code changes required to `BallisticsSystem.js` itself.
- Should include a simple reset behavior (targets return to their neutral state after a few seconds, or on a manual debug key press) so repeated testing sessions don't require reloading the whole level.

## 12. `/tools/generateLevelGeometry.js`

Documents and implements the one-time production pipeline for the three `.glb` level files plus their matching metadata JSON files. Per the standing asset policy (Document 1, Section 7), this script may use **any technique internally** — hand-authoring in Blender and exporting directly, a scripted Blender Python automation pipeline invoked from Node, or procedural JavaScript/Node geometry construction that is then serialized out to a real `.glb` file via a glTF exporter library — the only hard requirement is that running this script (or the equivalent manual DCC-tool workflow) produces **real, committed files under `/assets`** that the running game then simply loads. The running game itself must never construct this level geometry live at play-time.
